# RoboAlgo — End-to-End Audit, 2026-10-06

Scope: full codebase correctness, UI/UX wiring, dead code, plus two requested integrations
(TradingView full-universe ticker data, and validation-gate methodology from a supplied X
thread).

Baseline before this work: commit `45c8615`, test suite **203 passed / 9 failed**.
Nothing in this audit has been committed. All findings below carry a command that reproduces
them — a claim without a reproduction is marked as such.

---

## Verdict in one paragraph

The system had **two defects that could produce a wrong trade** and **one that silently
froze the entire screener**, none of which raised an error anywhere. The recurring failure
mode in this codebase is not crashes — it is *silence*: NaN swallowed as a warning, an empty
DataFrame returned on a permanent API refusal, a table that stops updating because nothing
schedules it, a ticker that stopped trading seven months ago still ranked #1. Everything
found here was found by running a command, not by reading code. Where a measurement
contradicted an assumption, the measurement won — including when the assumption was mine.

## The X thread — what "apply within" actually meant

Source: *"How to Use GPT-6 Astra to Find Profitable Trading Strategies 24/7"* (@RohOnChain).
The post itself was paywalled (HTTP 402); substance recovered via search.

It proposes an agent that continuously discovers strategies, each gated on
**Sharpe > 1.5, max drawdown < 15%, hit rate > 55%, t-stat > 2.0**.

**The gates do not work as stated, and this was measured rather than argued.**
Best-of-500 **pure Gaussian noise** (seed 42, 500 series) reached an annualized
**Sharpe of 2.379**, hit rate 0.550, drawdown 9.03% — comfortably clearing every one of the
thread's thresholds. Ranked on the first half and tested on fresh noise, the same winner
went from in-sample Sharpe **3.03** to out-of-sample **−2.77**.

The missing ingredient is a multiple-testing correction. Searching "24/7" means an unbounded
number of trials, and the maximum of N draws from noise grows with N.

**What was implemented instead:** `strategy_validation/gates.py` adopts the *structure* — an
explicit barrier every candidate must clear — and adds what the thread omits:
- Bailey & López de Prado deflated Sharpe (the original; a widely-circulated variant is
  wrong — it passes Sharpe 3.0 and rejects 1.8)
- mandatory in-sample / out-of-sample separation
- rejection when the trial count is undeclared or unverifiable, because that single input
  disables the entire correction

Result: the best-of-500 noise scores DSR 0.6156 → **rejected**. Twenty independent
best-of-100 searches → **0 passed**. A genuinely strong synthetic strategy (OOS Sharpe 2.0,
DD 8%, hit rate 0.60, 200 trades, 5 trials) → **approved**, so the gate is not merely
rejecting everything.

**Not wired into the live trading path.** It would change which strategies may trade real
money, and that is the operator's decision, not an audit's.

The thread's named strategies (Ornstein-Uhlenbeck stat arb, Avellaneda-Stoikov market
making, Hawkes order flow, Heston vol, FX carry) were **not** implemented: all need L2
order-book or options-surface data and market-making infrastructure this system does not
have, and several are latency-sensitive in a platform whose data was 7 days stale. The
transferable idea was the enforced barrier, not the strategy list.

## TradingView — what was integrated, and the decision you still own

`scanner.tradingview.com/america/scan` works unauthenticated, returns the full US universe
(**11,871 stocks**), and supports server-side filtering: a $1–$20 / >1M-volume screen
returned **719 survivors in 0.20s in a single request**. The current architecture downloads
tickers individually via yfinance and is capped at 3,000 to stay under ~45s. This is a
genuine improvement in both coverage and latency.

TradingView's **GitHub org has no public data API** — `scanner_data` is an archived static
Pine/JSON config repo. The scanner endpoint is the only real mechanism.

**The decision that is yours, not mine:** TradingView's Terms of Service prohibit scraping
and redistribution. This endpoint is undocumented and can be rate-limited, changed, or
removed without notice. The integration is therefore built as **one pluggable provider
behind a working fallback** — polite rate limiting, 900s cache, no redistribution, and a
clean degradation to the existing yfinance path, with `stats.stage1_source` reporting which
path actually ran so a scan can never misrepresent its own source. **If the answer is no,
the yfinance path still works and the provider can be disabled without touching anything
else.**

The reasons that actually matter:

- **OpenStock is AGPL-3.0.** RoboAlgo is a network service on Render, so copying its code in
  would put *our* source under AGPL. That is a licensing decision, not a technical one.
- **`tradesdontlie`'s own disclaimer forbids "automated trading or algorithmic
  decision-making using extracted data"** — which is precisely what we would use it for. It
  also drives the TradingView *desktop app* over Chrome DevTools Protocol, so it cannot run
  on Render at all.
- **`atilaahmettaner` feeds TradingView's `RSI`, `MACD`, `SMA20`, `EMA200` straight into
  BUY/SELL output** — the exact hazard in finding #1. It wraps the same endpoint we already
  call, so it adds no data we lack and adds a bug class we deliberately guarded against.
- **`Mathieu2301`** speaks TradingView's private chart websocket using browser headers and
  optional account cookies — the highest ToS exposure of the five — and needs a Node sidecar.
- **TradingAgents does not change our earlier rule-based-personas decision.** Its paper
  (arXiv 2412.20138) reports Sharpe ratios of 8.21 / 6.39 / 5.60 — *attributed, not
  endorsed* — over **three months of 2024 in a single regime, on three tickers, with no
  held-out period and no multiple-testing correction**. Its own README says results are
  non-deterministic and not guaranteed to match published figures, its `backtest.py` says it
  is "not a portfolio simulator", and its changelog records look-ahead leaks fixed as late as
  v0.4.0 with no indication the paper's runs were redone. It is the same methodology problem
  as the X thread, with a bigger number attached.

The only transferable idea: benchmark-relative settlement scoring for logged verdicts
(`lab_engine/verdict_log.py`).
